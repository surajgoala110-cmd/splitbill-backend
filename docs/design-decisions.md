# Design decisions

## 1. API contract

### Evidence and confidence

The available frontend excerpt confirms `POST /groups` and `GET /groups/:group_id`. The complete `src/api/client.ts` and `src/types.ts` files are not available, so the remaining endpoints and shapes below are implementation assumptions rather than confirmed frontend behavior. The service supports both the confirmed no-prefix paths and the original `/api/...` aliases.

All endpoints use JSON. `:groupId` is a path parameter, not a literal string. IDs are opaque strings generated by the service. Amounts are positive integer currency units, such as whole yen.

### Resource shapes

```json
{
	"id": "grp_1",
	"name": "Dinner",
	"members": [
		{ "id": "mem_2", "name": "A" }
	],
	"expenses": [
		{
			"id": "exp_5",
			"description": "Dinner",
			"amount": 1000,
			"paidBy": "mem_2",
			"participants": ["mem_2"],
			"createdAt": "2026-10-22T13:22:31Z"
		}
	]
}
```

The derived response shapes are:

```json
{ "memberId": "mem_2", "balance": 666 }
```

```json
{ "from": "mem_3", "to": "mem_2", "amount": 333 }
```

An empty collection is returned as `[]`, not `null`. Errors use `{ "error": string }`. Invalid JSON, missing required fields, non-positive amounts, unknown member IDs, and duplicate participants return `400`. A duplicate member name returns `409`; an unknown group returns `404`; unsupported methods return `405`.

## 2. Settlement rules and assumptions

- An expense has one payer and one or more participants. The amount is shared equally among the listed participants. The payer does not need to be a participant.
- A member's balance is `total paid - total owed`. A positive balance means the member should receive money; a negative balance means the member should pay money.
- Only expenses affect balances. The API does not record a completed payment or subtract a transfer from the calculated result.
- The participant list is part of each expense, so different expenses may involve different subsets of the group.
- Every expense amount must be a positive integer. This implementation assumes the smallest currency unit is an integer and does not accept decimals.
- Participants must be unique existing members. `paidBy` must also identify an existing member.

### Remainders

For an expense with amount `A` and `N` participants, each participant first receives an owed amount of `floor(A / N)`. The first `A mod N` participants in the request order receive one additional unit. For example, `100` split among three participants becomes `34, 33, 33`.

This rule is deterministic, preserves the exact total, and makes the ordering decision visible to the caller. It does mean that participant order has a one-unit effect when an amount is not evenly divisible.

### Settlement algorithm

1. Accumulate each member's total paid and total owed across all expenses.
2. Compute each balance as paid minus owed.
3. Put positive balances into a creditor list and negative balances, made positive, into a debtor list.
4. Match the first debtor with the first creditor for the smaller of the two remaining amounts.
5. Emit that transfer, remove any exhausted side, and continue until all sides are exhausted.

The calculation conserves money because the sum of all balances is zero. It also avoids unnecessary transfers for this creditor/debtor matching strategy, although the exact order is determined by member order and is not globally optimized for every possible objective.

## 3. Chosen design and rationale

- **Language and HTTP layer:** Go with the standard `net/http` package. It keeps the service small, has no third-party runtime dependency, and is straightforward to build in the provided Docker image.
- **Data structures:** A `Store` owns a map of group IDs to groups and a mutex. A group contains members and expenses. Expenses retain the original participant order so remainder allocation is reproducible.
- **Money representation:** `int64` integer units. This avoids floating-point rounding and makes conservation checks exact.
- **Concurrency:** The store uses read/write locking. Reads clone slices before responding, so callers cannot mutate store-owned slices through response data.
- **Persistence:** In-memory storage was selected because the brief did not provide a database requirement or frontend lifecycle expectations. It also keeps `docker compose up` self-contained.
- **Container:** A multi-stage Docker build compiles a static Go binary and runs it in Alpine. Compose exposes port `8080` as required.

## 4. Options considered and rejected

### SQLite or another database

Persistence would survive restarts and support multiple API instances, but it would add schema, migration, driver, and deployment decisions that cannot be validated against the missing contract. The current `Store` is the replacement boundary for a future repository implementation. The trade-off is data loss on restart and no horizontal scaling.

### Floating-point or decimal arithmetic

Floating point was rejected because it can make equal splits and total conservation depend on representation error. Decimal strings could support fractional currencies, but the currency and precision were not confirmed. Integer minor units are exact and simple, at the cost of not supporting fractions smaller than the chosen unit.

### Global optimization of transfers

An algorithm that searches for a globally minimal or specially ordered transfer graph could produce a different presentation of the same balances. The greedy creditor/debtor matcher is deterministic, linear in the number of members, and sufficient for the stated calculated-settlement scope. The trade-off is that its ordering is not optimized for preferences such as minimizing payment edges under every possible balance arrangement.

### Completed-settlement records

A payment workflow would need transfer IDs, idempotency, authorization, status transitions, and conflict handling. None was established by the available brief, so settlements remain derived read-only output. The trade-off is that the API cannot track whether a suggested transfer was actually paid.

### Response envelopes and pagination

Envelopes such as `{ "data": ... }` and paginated collections can help evolve APIs, but adding them without frontend evidence risks breaking the expected response shape. The implementation returns direct arrays and objects and leaves pagination out of scope.

## 5. Unconfirmed behavior and intentional scope

The following could not be confirmed from this workspace:

- The real frontend endpoint paths, field names, response envelopes, and error format.
- Whether amounts represent yen, another currency, or fractional currency units.
- Whether a payer must always be included among participants.
- Whether remainder units should go to the first participants, the payer, the highest shares, or another designated member.
- Whether settlement ordering or the number of transfers has a user-visible optimization requirement.
- Authentication, authorization, users, ownership, and multi-tenant isolation.
- Durable storage, concurrent replicas, backups, and data retention.
- Editing or deleting groups, members, and expenses.
- Settlement confirmation, payment records, idempotency, and audit history.
- Pagination, filtering, sorting, CORS, rate limiting, and production observability.

These areas are intentionally excluded rather than guessed. The current service is a single-process calculation API with no authentication, durable storage, CORS policy, or payment integration.
